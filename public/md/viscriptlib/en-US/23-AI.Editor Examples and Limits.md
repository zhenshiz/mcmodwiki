<h1 id="ai-editor-examples-and-limits" data-toc-id="ai-editor-examples-and-limits">AI editor examples and limits</h1>
<p>A shared chat menu does not imply identical editing tools in every editor. Ask AI to read the active project and available tools before requesting domain changes. Adapted editors share the <a href="?file=&quot;AI.Preview Apply and Undo&quot;">isolated draft, preview and whole-turn history workflow</a>.</p>
<h2 id="integrated-editors" data-toc-id="integrated-editors">Integrated editors</h2>
<table data-type="custom-table" data-with-header-row="true" style="min-width: 100px;">
<tbody>
<tr><th>Editor</th><th>Available domain operations</th><th>Outside the chat workflow</th></tr>
<tr><td>ViScriptShop</td><td>Shop settings, category/product CRUD, item/count, currency price, stock, experience and buying/selling type.</td><td>Promotions, stage restrictions, trade commands and custom components are outside the current adapter. Save/upload separately.</td></tr>
<tr><td>ViScriptRecipe</td><td>Registered recipe schemas and data, recipe-ID CRUD, enabled state and ADD/REPLACE/REMOVE mode.</td><td>Only actually installed and registered recipe types are available. Check the owning mod’s runtime reload requirements.</td></tr>
<tr><td>ViScriptQuests</td><td>Root/subquest graph nodes, constants, variables, positions and wires, checked by the native quest compiler.</td><td>Player-instance progression, reward execution and server publication are not direct chat operations.</td></tr>
<tr><td>ViScriptNpc: NPC and standalone behavior</td><td>Declared persisted configuration and behavior nodes, parameters, wires and variables, checked by native validation.</td><td>Arbitrary unknown fields, world spawning, debugging and publication use their normal paths.</td></tr>

<h2 id="shop-explicit-counts-and-prices" data-toc-id="shop-explicit-counts-and-prices">Shop: explicit counts and prices</h2>
<pre language="plaintext" isclosed="false"><code class="language-plaintext">Read the current shop and list its categories without changing them.
Preserve existing categories and add a currency category named Travel supplies.
Add minecraft:bread: 4 items per purchase, price 2, stock 20.
Summarize the actual changes and leave the draft for confirmation.</code></pre>
<p>Check the category type, actual item, result count, unit price and stock. Configure promotions or stage restrictions manually in their forms after applying the supported changes.</p>
<h2 id="recipes-query-the-available-type-first" data-toc-id="recipes-query-the-available-type-first">Recipes: query the available type first</h2>
<pre language="plaintext" isclosed="false"><code class="language-plaintext">Query the recipe types and editable fields actually registered in this editor.
Preserve existing recipes and add a uniquely identified shaped recipe:
three minecraft:wheat in a row produce one minecraft:bread, using ADD mode.
Use the exact returned type and schema, validate it and show a preview.</code></pre>
<p>Inspect the recipe ID, ingredient pattern, output count and mode. A prompt cannot create compatibility with an uninstalled mod or an unregistered recipe type.</p>
<h2 id="quests-choose-the-right-graph" data-toc-id="quests-choose-the-right-graph">Quests: choose the right graph</h2>
<pre language="plaintext" isclosed="false"><code class="language-plaintext">Read the current root graph and available node catalog first.
Then query the objective and reward catalog inside the intended subquest.
Add an objective for 16 minecraft:oak_log and connect it to that subquest flow.
Preserve the existing structure, use exact node keys and ports, and preview after validation.</code></pre>
<p>The default <code>graph</code> is <code>root</code>; subquest operations identify the owning subquest node by UUID. Query objectives and rewards in the subquest catalog. Use <code>item_stack</code> for the item and the <code>item_count</code> input constant for its quantity. Use returned constant keys and raw values.</p>
<h2 id="npcs-constrain-sections-and-graph-parameters" data-toc-id="npcs-constrain-sections-and-graph-parameters">NPCs: constrain sections and graph parameters</h2>
<pre language="plaintext" isclosed="false"><code class="language-plaintext">Read the editable configuration sections, field schemas and behavior catalog.
Change only the appearance or equipment fields I specify, preserving other sections.
For behavior changes, describe the node/wire plan and use graph tools to produce a validated draft.</code></pre>
<p>Use actual section IDs and declared fields. Node parameters follow the catalog types; disconnect a wired input before replacing it with a constant. The <code>npc_ai</code> section directly exposes only its enabled state; maintain behavior structure through graph operations.</p>
<h2 id="registry-queries" data-toc-id="registry-queries">Registry queries</h2>
<ul>
<li><p>Prefer complete IDs such as <code>minecraft:iron_ingot</code>; localized-name search depends on loaded language resources.</p></li>
<li><p>Ask for members of <code>#minecraft:logs</code> to inspect a specific tag. Say “search item tags” when you want tag IDs themselves.</p></li>
<li><p>Continue with the tool’s returned next page when needed. The per-page setting does not restrict reading to the first page.</p></li>
<li><p>Queries use loaded or synchronized registry data. They do not grant arbitrary-file access, command execution or access to private server state.</p></li>
</ul>
<p>A useful prompt sequence is: read, identify the target, state what to preserve, validate and preview. Model/service quality still determines the generated proposal.</p>
